# Trae2api-cn 仓库分析报告

> 分析对象：https://github.com/autumnsentiment/Trae2api-cn
> 分析版本：main @ `2f2dc1a`（v1.0.6，2026-10-17）
> 分析方式：完整源码静态阅读（约 3.3 万行 Python + 内嵌前端），未运行服务、未接触任何 Trae 账号

---

## 1. 一句话结论

这不是一个"模型实现"项目，而是一个**针对 Trae（字节跳动 AI IDE / SOLO）私有协议的逆向反代网关**：它把 Trae 桌面客户端的登录凭据、Remote/IDE/Solo/Work 四条私有模型通道，包装成 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 三套标准协议，并附带账号池、每日签到、积分记账和一个网页控制台。

工程完成度相当高（942 个测试、详尽的 README、非 root 容器、CI 门禁），但**安全模型是"内网可信"假设**，且核心能力建立在对上游服务条款和风控的绕过之上。它适合做协议研究/自用内网代理，**不适合直接暴露公网或用于商业分发**。

## 3. 它到底在做什么

### 3.1 请求主链路

```
调用方 (Codex / Claude Code / new-api / OpenAI SDK)
        │  OpenAI / Anthropic / TraeWork 私有协议
        ▼
FastAPI 单进程 ── auth_middleware（RELAY_API_KEYS，可整段关闭）
        ▼
协议归一化：handle_chat / handle_responses / anthropic / _handle_traework_custom
        ▼
会话与账号绑定 _bind_chat_session
   · session lease（会话粘住某个账号的 JWT，避免并发切号串账）
   · 轮询选号：round-robin 或 credit-priority
   · 每账号 asyncio.Semaphore 并发槽 + 排队超时
        ▼
路由决策 _dispatch_chat
   · auto-route（带 tools → IDE，纯聊天 → Remote）
   · task routing（model=auto → flash / 6.1sol）
   · 多模态自动换模型
   · 端点回退链：首选端点失败 → Remote（仅在"未产生任何输出"时允许）
        ▼
传输适配器
   remote  : POST /chat_sessions → GET /chat_sessions/{id}/events (SSE)
   ide/solo: POST /api/ide/v2/llm_raw_chat（原生 tools）
   work    : remote 会话固定 agent_id=solo_work_remote
   raw     : llm_raw_chat v2（个人账号缺企业 app config，已降级为内部诊断）
   cli     : 本机 traecli 子进程
   native  : Windows helper 加载 ai_agent.dll + ZeroMQ/AHA IPC
        ▼
sse.py 翻译：thinking 分离、tool_calls 增量拼接、JSON 修复、usage 映射、心跳
        ▼
_UsageTracker → data/usage_records.json + usage_stats.json（积分异步 enrichment）
```

### 3.2 认证来源（这是项目的"入口"）

- `auto`：读取本机 `%APPDATA%\Trae CN\User\globalStorage\storage.json`，用**硬编码的 4 个 64 字节盐**做 `SHA-512` 派生 AES-128-CBC 密钥并解密（`src/trae_decrypt.py`）。
- `web-login`：OAuth 授权码流程。因为 Trae 强制回调 `http://127.0.0.1:<port>/authorize`，所以项目让用户下载一个**本机 Python 小助手**（`web_login.py`）接收回调再转发给 relay。
- `env` / `manual` / `cli`：环境变量、抓包得到的 Cloud-IDE-JWT、本地 CLI 子进程。

值得注意的是固化了官方桌面客户端的 `client_id = ono9krqynydwx5`，即**冒充官方客户端**与上游通信。

### 3.3 账号池与"运营"能力

`auth.py` 把凭据持久化到 `data/accounts.json`，并实现了：顺序/积分优先轮询、单账号模型请求开关、每日签到（北京时间定时）、9074 风控码自动**轮换设备 ID + 指数退避**、积分快照对账、按请求记账。README 明确写了这是为了"多账号并发"与"签到领积分"。

## 4. 工程质量：哪些地方做得确实好

1. **测试密度罕见**。942 个测试、包含离线协议回放（`test_offline_chain_replay.py`）、假 CLI（`tests/fake/`）、SSE 逐帧断言（`test_sse.py` 99KB）、会话取消/回收（`test_session_cancellation.py` 45KB）。
2. **"不撒谎"的数据契约**。tokens 来源未知时显示 `--` 而不是 0；积分账单未落库显示"结算中"；`tool_execution` 固定上报 `client`；`/v1/status` 暴露 build revision 便于确认容器与源码一致。
3. **防重复扣费的克制**。只在"首个模型事件之前"允许空响应重试；一旦出现输出/provider/usage/工具事件就绝不重放——这是踩过重复计费坑才会写的约束（`src/main.py:11098` 附近）。
4. **并发正确性意识强**。session lease 把账号与 JWT 一起冻结，避免"切号后 A 的 token 被 B 记账"；刷新 token 时用"捕获快照 + 对比 refresh_token"丢弃过期响应（`src/auth.py:347`）。
5. **部署规范**。Docker 非 root、HEALTHCHECK、`.dockerignore` 排除 `data/`、CI 先跑测试再发版、GHCR 出 amd64/arm64。

## 5. 问题与风险（按严重度）

### 🔴 严重：管理 API 完全绕过鉴权

`src/main.py:602` 的 `PUBLIC_PATHS` 把**整个控制台后端**列进了白名单：

```
/api/accounts  /api/accounts/switch  /api/accounts/remove  /api/settings
/api/web-auth  /api/logout  /api/polling*  /api/checkin/*  /api/usage/*
/api/overview  /api/max-mode*  /api/auto-route  /api/auto-checkin*
```

而 `auth_middleware`（`src/main.py:12289`）在白名单命中时直接 `call_next`，各 handler 自身也**没有任何二次校验**。后果：

- 只要端口可达，**即使设置了 `RELAY_API_KEYS`**，任何人都能：读取账号列表、切换/删除账号、触发签到、读取全部消费记录；
- `POST /api/settings` 可修改上游 `web_base_url`/`model_base_url`——把后续请求（含携带 `Authorization: <JWT>` 的请求）导向攻击者主机，等价于**凭据外带**；
- `POST /api/web-auth` 可向账号池注入任意凭据。
- `/api/model-test` 额外有一条"私网/回环 IP 免鉴权"分支（`src/main.py:12293`），把安全性押在 `request.client.host` 上——反向代理后该值恒为代理 IP，判断会整体失真。

README 里"管理接口对内网地址免鉴权"的描述与实现并不一致：实现是**无条件公开**，不是"仅内网"。

### 🔴 严重：凭据以明文形态多处落盘/落日志

- `data/accounts.json` 明文保存 `token` + `refresh_token`；
- `_save_env_snapshot()`（`src/auth.py:659`）把当前 JWT/refresh token **回写进 `.env`**；
- `AuthState.log_summary()`（`src/auth.py:84`）打印 `token[:36]`——JWT 前 36 字符已包含 header 与 payload 开头（alg/kid/iss/uid 一类字段）；
- `auto` 模式的"解密"本质是**混淆**：盐硬编码在源码里，密钥由密文自身前 32 字节派生，拿到 `storage.json` 的任何人都能还原。它防的是"随手一看"，不是攻击者。

### 🟠 高：主动对抗上游风控 + 共享订阅额度

9074 风控码自动换设备 ID、退避重试、多账号轮询把同一订阅的额度摊到并发请求上——这些是明确的**服务条款规避**行为。风险不是理论上的：账号封禁、额度清零、法务风险都由使用者承担。README 也写了"请自行承担账号风险"，但项目本身把"绕风控"做成了功能特性。

### 🟠 高：relay 主机上的本地代码执行面

- `cli` 模式（`src/cli_client.py`）在 relay 主机上起 `traecli` 子进程，默认禁用 `Read,Bash,Edit,Replace,Write,Glob,Grep,Task`，但该名单可用 `TRAE_CLI_DISALLOWED_TOOLS` 覆盖；一旦放开，模型输出即可在服务器上执行命令/读写文件。
- `traework-native` 模式在 Windows 主机加载专有 `ai_agent.dll`，通过 ZeroMQ/AHA IPC 与 TraeWork 通信（`native/README.md`）。这是把"客户端进程内协议"整个搬到服务器侧，攻击面与合规风险都显著。
- 仓库本身不分发 DLL，但 helper 具备任意本地 IPC 能力。

### 🟡 中：架构与可维护性

- `main.py` **13,383 行 / 614KB**，其中约 3,000 行是内嵌的 HTML+CSS+JS 控制台（`src/main.py:1033` 起）。路由、调度、签到、记账、前端模板全在一个模块，`main` 反向依赖所有传输层。
- 同一套"OpenAI → 上游"的转换逻辑在 `sse.py` / `trae_client.py` / `raw_client.py` / `responses_api.py` / `traework_compat.py` 各有一份，语义漂移风险高（工具调用尤其）。
- 全部状态在进程内：session lease、`previous_response_id` 缓存（TTL 3600s / 1024 条）、用量队列、账号轮询游标。**不能水平扩展**，重启即丢 Responses 续轮上下文；`uvicorn` 单进程。
- 只有 `pytest` 进 CI；`pyproject.toml` 配了 ruff 但没有 lint/type 门禁，也没有 mypy。

### 🟡 中：供应链与运行面

- 依赖只写范围（`fastapi>=0.115,<1` 等），无 lock/hash；构建不可复现。
- 推荐用 `ghcr.io/...:latest` 部署，镜像 tag 可变；Actions 用 `@v4/@v5/@v6` 大版本 pin（常规但非 SHA pin）。
- 默认 `HOST=0.0.0.0`、`RELAY_API_KEYS` 默认为空 → 开箱即"无鉴权 + 全接口公开"。README 有警告，但默认值决定了大多数人会这样跑。

### 🟢 低：前端与细节

- 控制台大部分输出走了 `escapeHtml`，但仍有若干字符串拼接未转义（如 `route.text`、`usageModelFlags` 的 badge HTML）；目前这些值来自内部常量/枚举，风险有限，但一旦上游模型名/账号标签被拼进去就会变成存储型 XSS。
- 文本工具桥（remote/work/raw）靠系统提示注入工具定义，再从模型自由文本里解析 `tool_calls`；`_repair_json_arguments` 之类的启发式能救回大部分情况，但本质脆弱，且把工具 schema 全量塞进提示词会显著增加输入 token。
- 计费依赖"上游 credits 差值 + 异步回合查询"；同账号高并发下仍可能出现归属模糊（代码用 `reply_to_message_id` 做了缓解，但 README 自己承认会出现 `--`）。

## 6. 如果你要用它：最低限度的加固清单

1. **永远设置 `RELAY_API_KEYS`**，并且**不要**因此以为管理面安全了——在前面加一层反代，把 `/api/*` 与 `/web/*` 限制到管理网段或加 Basic Auth。
2. **绝不裸奔公网**：只监听内网/回环，外面套 TLS；`/api/settings` 能改上游地址，等于半个 RCE 前置条件。
3. 把 `data/` 当机密目录（0700），`.env` 不进镜像不进 git；日志采集侧做 token 脱敏。
4. 不要在生产机用 `auto` 认证（会去读本机 Trae 登录态）；用独立容器 + 独立账号。
5. 关掉不用的传输：`cli` / `traework-native` / `raw` 都别开；`TRAE_CLI_DISALLOWED_TOOLS` 不要放开。
6. 单实例部署即可；要扩容先接受"会话粘性 + 重启丢上下文"。
7. 合规上把它当"协议研究工具"，别对外提供服务，别接商业计费链路。

## 7. 想改代码的话，优先级建议

| 优先级 | 改动 |
|---|---|
| P0 | 把 `/api/*`、`/web/*` 从 `PUBLIC_PATHS` 移除，改为独立 admin token / 会话 cookie；`/api/settings` 的上游 URL 做 allowlist（只允许已知 Trae 域名） |
| P0 | 日志与异常脱敏（token、refresh_token、Authorization），`accounts.json` 至少做文件权限 0600 + 可选 OS keyring |
| P1 | 拆 `main.py`：`routes/`、`console/`（模板独立文件）、`dispatch.py`、`usage.py`、`accounts.py` |
| P1 | 统一协议转换层，消除 `sse/raw/trae_client/responses` 四份重复；补 contract test |
| P2 | 引入 `uv lock` / `pip-compile` + hash；CI 加 ruff + mypy |
| P2 | 把进程内 session/response 缓存抽象成可替换后端（内存 / Redis），为多副本铺路 |
| P3 | 前端拼接全部走 `textContent`/模板转义；移除 `innerHTML` 拼接路径 |

## 8. 同类项目定位

搜索可见的同类项目（`JeffHu0912/trae2api`、`linqiu919/trae2api`、`lftk/trae-api`、`FuSheng-cs/Trae2api-dsh` 等）解决的是同一个问题——把 Trae 通道转成 OpenAI 兼容 API。本仓库的差异点在于：

- 协议覆盖最全（Chat + Responses + Anthropic + TraeWork 私有入口）；
- 唯一做了多账号池 + 签到 + 积分记账 + 控制台的；
- 文档与测试投入明显高于同类（README 40KB、`.env.example` 14KB 注释、逆向报告 `docs/zedex-chain-diff.md`）；
- 也因此在"合规风险"上走得更远（主动风控对抗、账号池化）。
