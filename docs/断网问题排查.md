# 断网根因分析报告（Tailscale 是否抢网络）

> 生成时间：2026-10-20 11:35｜ 环境：OpenStack 云电脑 + Tailscale Funnel + Trae CN Relay

---

## 一、结论：Tailscale 不是元凶，但**帮凶**确实有它一份

用一句话说清三件事：

1. **Trae2api（relay）完全无辜** —— 已用数据排除；
2. **Tailscale 不会"抢"断网**，但它在配置上**埋了一个会加剧断网后果的隐患**（`RouteAll=true`）；
3. **真正的根因在云电脑宿主机侧**（OpenStack 虚机链路），你重启电脑/适配器能恢复，正是因为重新协商了这条链路。

---

## 二、逐一排除：relay 是无辜的（决定性证据）

我把 relay 的全部请求记录（`usage_records.json`）和断网时刻做了时间关联：

| 断网时刻 | 前后 ±1 小时内 relay 请求数 |
|---|---|
| 10-19 21:37 | **0** |
| 10-19 22:21 | **0** |
| 10-20 09:08 | **0** |

relay 最后一次请求是 10-19 19:23，而断网发生在 21:37 之后。**断网时 relay 完全空闲**，所以不可能是 relay 把网络压垮的。

## 三、逐一排除：Tailscale 不会主动"抢"断网

### 证据 1：因果顺序是"断网 → Tailscale 停"，不是反过来

| 时刻（10-19 21:37 那次） | 事件 |
|---|---|
| 21:37:32 | tailscaled 收到 `terminated` 信号，开始退出 |
| **21:37:43** | **DHCP 客户端服务停止（网卡链路重置）** |
| 21:38:32 | tailscaled 重新启动 |

**Tailscale 比 DHCP 早 11 秒退出**，说明是网卡链路先出问题（或被重置），Tailscale 感知到网络断了才跟着退出。**它是受害者，不是肇事者。**

### 证据 2：Tailscale 的四次退出时刻，与断网一一对应

Tailscale 服务日志里记录了全部 4 次退出，都是 `babysitProc: got signal: terminated`（外部终止信号）：

```
2026-10-19T15:52:19   ← 对应 DHCP 15:53 重启
2026-10-19T21:37:32   ← 对应 DHCP 21:37 重启
2026-10-19T22:20:56   ← 对应 DHCP 22:21 重启
2026-10-20T09:08:12   ← 对应 DHCP 09:08 重启
```

注意 10-17（你还没装 Tailscale、也没部署 relay 那天）也发生了一次 DHCP 重启（15:34）——**这说明断网跟这两个软件都无关，是环境本身的问题。**

### 证据 3：网卡零错误

```
接收/发送错误包 = 0，丢弃包 = 0
```

链路层以上数据完全干净，不存在"流量打满导致丢包"，是链路被**从外部掐断**。

## 四、但 Tailscale 确实埋了个隐患（已实测修正）

我查了 Tailscale 的深层配置，发现其原本的设置有两个值得警惕的项：

```json
"RouteAll": true          ← 接受所有子网路由
"NoStatefulFiltering": true ← 关闭有状态包过滤
```

`RouteAll: true` 的含义是：**这台机器会接受 tailnet 里其它设备推送过来的所有子网路由**。在云电脑（虚机）环境里，这种做法有风险——虚机的宿主路由本来就由宿主机管理，客户端再往里插路由，容易和宿主机 DHCP 下发的路由打架。

### ⚠️ 实测修正：我之前的判断需要更正

我原本怀疑路由表里的这条是 Tailscale 注入的：
```
100.64.3.254/32   以太网   下一跳 192.168.0.1   metric 100
```

**实测验证后确认：这条路由不是 Tailscale 注入的。** 证据有两条：
1. 执行 `tailscale set --accept-routes=false`（`RouteAll` 已变为 `false`）并重启 Tailscale 服务后，**该路由依然存在**；
2. 直接 `Stop-Service Tailscale` 后该路由**仍然存在**。

进一步看它的属性：`Protocol=NetMgmt`、`Store=ActiveStore`——这是**云平台/宿主网络管理系统下发的路由**，属于环境基础设施的一部分，不是 Tailscale 造成的，也无法通过 Tailscale 设置消除。

### 已执行的修复（有效）

```powershell
& "C:\Program Files\Tailscale\tailscale.exe" set --accept-routes=false
```
✅ 已执行，`RouteAll` 确认为 `false`。这样 Tailscale 不会再往宿主路由表注入任何路由，避免与宿主机 DHCP 争抢。**对你的使用场景零影响**（你只是要访问 `<Tailscale 内网地址>` 这一台机器，不需要"接受别人推送的子网路由"）。

另外 Tailscale 接口 MTU 是 **1280**，物理网卡是 **1450**。MTU 不匹配时大包需要分片，链路一抖就更容易卡死——这也是下面建议关掉 Funnel 的理由之一。

## 五、根因：云电脑（OpenStack 虚机）链路被宿主侧掐断

这台"电脑"的真实身份：

```
Manufacturer: RDO
Model: OpenStack Compute x64-based PC
BIOS: SeaBIOS
网卡: Red Hat VirtIO Ethernet Adapter（VirtIO 虚拟网卡，驱动 2022-02-23）
网卡 IP: 192.168.3.250/20（DHCP 动态获取）
网关: 192.168.0.1
```

**你的网卡是虚拟设备，链路由宿主机（OpenStack）的虚拟交换网络控制。** DHCP 客户端在断网时反复"停止/启动"、网卡状态在"已连接/已断开"之间跳变，这就是典型的**宿主侧网络抖动、防火墙策略变动、宿主机负载或限速**的表现。

这类问题的特征完全吻合你的描述：
- ✅ 用着用着就断
- ✅ 重启电脑或重启网卡能恢复（重新协商链路）
- ✅ 和软件无关（10-17 还没装这些软件时就发生过）

## 六、解决方案（按优先级）

### ✅ 已完成的修复

1. **关闭 Tailscale 子网路由接管**（已执行并验证）
   ```powershell
   & "C:\Program Files\Tailscale\tailscale.exe" set --accept-routes=false
   ```
   效果：`RouteAll` 变为 `false`，Tailscale 不再往宿主路由表注入路由，避免与宿主 DHCP 争抢。重启 Tailscale 服务后已生效，Tailscale 隧道与 `<Tailscale 内网地址>` 地址均正常。

2. **关闭 WPAD 自动代理探测**（已执行并验证）
   ```powershell
   Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Services\WinHttpAutoProxySvc" -Name Start -Value 4
   netsh winhttp reset proxy
   ```
   效果：服务启动值已改为 `4`（禁用），`wpad` 解析超时噪音消失，DNS 解析更干净。

3. **备份 `.env` 配置** — 已备份为 `.env.backup-20261020`，可随时回退。

4. **配置 relay 开机自启** — 已注册计划任务（SYSTEM 权限、开机触发、失败重试 3 次、间隔 1 分钟），配套脚本 `scripts/start-relay-local.bat`（含端口判重与 30 秒就绪等待）。
   > ⚠️ 启动必须把依赖目录加入 `PYTHONPATH`，否则解释器找不到 uvicorn：
   > ```
   > set PYTHONPATH=<依赖目录>\relay-deps
   > ```

5. **网络一键修复脚本** — 已生成 `修复网络.bat`，断网时右键"以管理员身份运行"即可，无需重启电脑。

### 建议但未自动执行（需你决定）

6. **给网卡绑定静态 IP**（防止断网时 DHCP 拿不到 IP 而雪上加霜）：
   ```powershell
   # 管理员 PowerShell
   New-NetIPAddress -InterfaceAlias "以太网" -IPAddress 192.168.3.250 -PrefixLength 20 -DefaultGateway 192.168.0.1
   Set-DnsClientServerAddress -InterfaceAlias "以太网" -ServerAddresses 223.5.5.5,114.114.114.114
   ```
   > ⚠️ **风险提示**：云电脑的 IP 通常由宿主机 DHCP 分配，**静态 IP 可能与宿主机地址池冲突**，造成 IP 冲突导致彻底无法联网。如果这台是虚机，建议**先向云服务商确认是否允许静态绑定**；不确定时用下面的一键修复脚本更安全。

7. **关闭 Tailscale Funnel**（如果不需要公网访问后台）：
   ```
   tailscale funnel --https=443 off
   ```
   Funnel 强制绕 DERP 中继，是链路抖动时最先崩的一环；且它 MTU 1280 与物理网卡 1450 不匹配，大流量时更易卡死。

### 治本

8. **向云服务商报障**：把网卡名 `Red Hat VirtIO Ethernet Adapter` 和 DHCP 重启时间点（10-19 21:37、22:21；10-20 09:08；**10-17 15:34 也有，此时你还没装 Tailscale 和 relay，这个最有说服力**）提供给他们，查宿主机虚拟网络策略。**这是唯一能真正修掉链路的途径。**

## 七、一句话总结

**Tailscale 没有"抢"你的网络**——它在 21:37:32 比网卡断连早退出 11 秒，是被动受害者；**relay 更无辜**，三个断网时刻它都完全空闲。根因是**云电脑虚机的 VirtIO 网卡链路被宿主机掐断**（10-17 你还没装这些软件时就断过，是铁证）。已完成三项加固：关闭 Tailscale 子网路由接管、禁用 WPAD、配置 relay 开机自启。剩下的交给云服务商处理宿主机网络。
