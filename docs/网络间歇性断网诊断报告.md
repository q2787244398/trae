# 电脑间歇性断网诊断报告

> 生成时间：2026-10-20 09:55 ｜ 环境：OpenStack 云电脑（RDO SeaBIOS，虚机）+ Tailscale Funnel + Trae CN Relay

---

## 一、结论：不是 Trae2api 造成的，是云电脑虚拟网卡链路抖动

你截图里的三张图分别说明：
1. Chrome 提示"无法访问 DNS 服务器"；
2. Windows 网络面板显示 **以太网「无法访问 Internet」**、Tailscale 也断开；
3. 系统建议"重启以太网网络适配器"。

而重启电脑 / 重启适配器之所以能恢复，是因为**重新协商了虚机网卡与宿主机的链路**，DHCP 重新拿到了 IP。问题出在这一层的物理/虚拟链路，而不是上层应用。

## 二、关键证据（从系统日志实测）

### 1. DHCP 客户端在反复停止/重启

近 3 天 DHCP 事件按小时统计（每天固定 2~3 组，每组 7 条）：

| 时间 | 事件数 |
|---|---|
| 10-17 15 时 | 7 |
| 10-19 01 时 | 7 |
| 10-19 02 时 | 7 |
| 10-19 15 时 | 5 |
| 10-19 21 时 | 7 |
| 10-19 22 时 | 7 |
| 10-20 09 时 | 7 |

对应的都是 `DHCPv4 客户端服务已停止（关机标记值 1）` → `已启动` 这一对。**DHCP 客户端停止意味着网卡链路被重置**，不是软件层能解释的。

### 2. Tailscale 是被"连带"停掉的，不是自己崩的

Tailscale 服务日志里明确写着：

```
client disconnected (S-1-5-21-...-500): disconnecting Tailscale
0CABAJCH-GIFD0V\Administrator signed out from session 1: disconnecting Tailscale
health(warnable=wantrunning-false): error: Tailscale is stopped.
```

这是**网卡断链后 Tailscale 被迫下线重连**的正常表现，属于结果而非原因。服务日志文件的轮转时刻（15:53、21:38、22:21、09:08）与 DHCP 重启时刻**完全重合**，进一步印证因果关系。

### 3. 网卡本身没有收发错误

```
接收/发送 错误包 = 0，丢弃包 = 0
```

说明**数据在链路层以上是干净的**，不是流量打满或硬件损坏，是链路被宿主侧掐断。

### 4. 这是一台云电脑（虚机）

```
Manufacturer: RDO
Model: OpenStack Compute x64-based PC
BIOS: SeaBIOS
网卡: Red Hat VirtIO Ethernet Adapter（VirtIO 虚拟网卡，驱动版本 2022-02-23）
```

你的"电脑"其实是**跑在 OpenStack 上的虚拟机**，网卡是虚拟设备。虚拟网卡的链路由宿主机的虚拟交换网络控制，**宿主侧的网络抖动、防火墙策略、宿主机负载或限速**都会直接表现为你这边的"断网"。

## 三、为什么感觉是"搭建 Trae2api 之后才开始"

时间上的巧合，加上三个放大因素（注意：这些不是根因，但会让问题更频繁、更容易被联想到 relay）：

1. **Tailscale Funnel 一直开着**（`tailscale status` 显示 `# Funnel on: - https://<你的中转域名>`）。Funnel 让 relay 通过 Tailscale 的 DERP 中继对外暴露服务，**流量要绕 DERP 转发**。链路一抖，Funnel 就先断，表现得特别像"网络没了"。
2. **relay 长时间大流量传输**：昨天到今天一天半时间 relay 处理了 480 万 token、100+ 次请求，每次都是几十 MB 级上下文上传，**持续占带宽**，虚机带宽余量小的时候更容易把链路问题放大成断流。
3. **relay 当前已停止运行**（8000 端口无监听、无 python 进程），说明断网期间服务也没了，容易误以为"是 relay 搞崩了网络"。

另外一个 DNS 相关的噪音：日志里有大量 `wpad` 解析超时（事件 1014）。`wpad` 是 Windows 的 WPAD 自动代理探测，**它本身无害**，但会在 DNS 不畅时反复重试、拖慢解析。这是虚机常见现象，不是断网原因。

## 四、怎么办（按性价比排序）

### 立刻能做

1. **给虚机网卡绑定静态 IP（治本）**：断网时如果 DHCP 拿不到 IP 会雪上加霜。管理员权限 PowerShell 执行：
   ```powershell
   New-NetIPAddress -InterfaceAlias "以太网" -IPAddress 192.168.3.250 -PrefixLength 24 -DefaultGateway 192.168.3.1
   Set-DnsClientServerAddress -InterfaceAlias "以太网" -ServerAddresses 223.5.5.5,114.114.114.114
   ```
   （IP/网关需按你实际网络调整，`ipconfig /all` 可查当前网关）
2. **自动修复脚本**（断网时不用重启电脑）：把下面内容存为 `修复网络.bat`，右键"以管理员身份运行"，几秒恢复：
   ```bat
   @echo off
   netsh interface set interface name="以太网" admin=disabled
   timeout /t 3
   netsh interface set interface name="以太网" admin=enabled
   ipconfig /flushdns
   ipconfig /renew
   ```
3. **关掉 WPAD 自动探测**，减少 DNS 噪音（管理员 PowerShell）：
   ```powershell
   Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Services\WinHttpAutoProxySvc" -Name Start -Value 4
   netsh winhttp reset proxy
   ```

### 减少复发/减轻影响

4. **关闭 Tailscale Funnel**（如果不需要外网访问 relay）。Funnel 依赖 DERP 中继，是链路抖动时最先崩的一环：
   ```
   tailscale funnel --https=443 off
   ```
   需要外网访问的话，改用 Tailscale 内网直连（tailnet 内其他设备访问 `100.x.x.x（Tailscale 内网IP）:8000`），不走 Funnel。
5. **降低 relay 的带宽压力**：大上下文任务错峰、优先用 Flash/Turbo 模型，减少并发上传量。虚机带宽余量小的时候这是最有效的减压。
6. **向云服务商报障**（这是虚机的根因）：把 DHCP 重启时间点（10-19 21:37、22:21，10-20 09:08）和网卡名 `Red Hat VirtIO Ethernet Adapter` 提供给宿主机管理员，让他查宿主机的虚拟网络/限速策略。这是唯一能真正修掉链路的途径。

## 五、一句话总结

你的断网是**云电脑（OpenStack 虚机）的虚拟网卡链路被宿主侧掐断**，DHCP 重启和 Tailscale 掉线都是结果；Trae2api 不是元凶，但 Tailscale Funnel + relay 的大流量传输放大了体感。治标靠静态 IP + 修复脚本，治本要云服务商处理宿主机网络。
